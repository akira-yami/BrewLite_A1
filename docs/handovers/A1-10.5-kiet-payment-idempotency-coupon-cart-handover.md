## 1. Quyết Định Kiến Trúc & Hướng Đi Kỹ Thuật (Architectural Decisions)

### 1.1. Hướng đi được lựa chọn

| Khu vực | Quyết định |
|---|---|
| Payment lifecycle | Điều phối trạng thái tại PaymentsService; kiểm tra Order, thời hạn giữ chỗ và tạo Payment PROCESSING trong transaction trước khi gọi gateway. |
| Retry | Order PAYMENT_FAILED được chuyển trạng thái qua transitionForPaymentRetry; lần retry dùng Idempotency-Key mới. |
| Concurrency | Khóa Order bằng SELECT ... FOR UPDATE để tuần tự hóa thao tác thanh toán/hết hạn trên cùng Order. |
| Database guard | Partial unique index giới hạn một Payment PROCESSING trên mỗi Order. |
| Coupon | Tập trung validate, consume và release redemption trong PromotionsService; Orders điều phối qua service này. |
| Expiry | Chỉ OrderExpiryJob sở hữu expiry lifecycle; job được đăng ký trong OrdersModule và chạy qua ScheduleModule tại AppModule. InventoryExpiryJob độc lập đã bị loại bỏ để mọi quyết định cancel/release nằm dưới Order row lock và cùng transaction. |
| Frontend | Dùng authenticated coupon API; chuyển coupon code từ CartDrawer qua menu/Checkout đến Create Order; dùng Order server trả về làm nguồn giá chính thức; lưu pending payment/key trong sessionStorage; áp dụng state transition thuần cho SUCCEEDED/FAILED/PROCESSING/UNKNOWN. |
| Verification | Bổ sung unit, integration, migration smoke và checkout E2E trong CI. |

### 1.2. Lý do lựa chọn (Rationale)

- **Transaction + row lock:** tránh việc Payment và Cron cùng cập nhật một Order dựa trên trạng thái đã cũ.
- **Idempotency kết hợp database constraint:** application xử lý replay theo key; PostgreSQL bảo vệ thêm invariant về Payment đang xử lý.
- **Tách gateway khỏi transaction:** tránh giữ transaction/row lock trong thời gian chờ phản hồi từ gateway.
- **Phân định module:** Promotions chịu trách nhiệm vòng đời coupon; Orders và Payments gọi service nghiệp vụ thay vì tự nhân bản quy tắc.
- **Kiểm tra lại trước khi expiry:** Cron khóa và đọc lại Order trước khi chuyển trạng thái.
- **Kiểm thử với PostgreSQL:** xác minh migration và hành vi database thực tế, thay vì chỉ dựa vào mock.

### 1.3. Trade-off Analysis

| Phương án khác | Hạn chế/rủi ro | Quyết định |
|---|---|---|
| Chỉ đọc trạng thái Order không khóa | Race condition khi nhiều tiến trình cập nhật đồng thời. | Dùng row lock trong transaction. |
| Chỉ kiểm tra idempotency ở application | Không bảo vệ đầy đủ invariant dữ liệu trước cạnh tranh. | Kết hợp application logic và unique index. |
| Retry với key cũ | Khó phân biệt lần thử cũ và lần retry mới; tăng nguy cơ replay. | Retry bằng key mới. |
| Để Orders Repository tự quyết toán coupon | Tăng coupling với Promotions. | Gọi PromotionsService. |
| Cron hủy mọi Order quá hạn ngay từ kết quả truy vấn | Có thể đụng Order đang có Payment PROCESSING. | Loại trạng thái đang xử lý và kiểm tra lại trong transaction. |
| Chỉ unit test bằng mock | Không chứng minh được migration/index/transaction trên PostgreSQL. | Bổ sung integration và migration smoke test. |

Đây là phân tích trade-off kỹ thuật, không hàm ý mọi phương án thay thế đều đã được benchmark hoặc thử nghiệm riêng.

### 1.4. Giá trị mang lại (Value Proposition)

- Hoàn thiện luồng retry thanh toán và kiểm soát replay/concurrent payment.
- Giảm nguy cơ Order bị hết hạn trong khi Payment vẫn đang xử lý.
- Đồng bộ vòng đời coupon và inventory khi thanh toán thành công, hủy hoặc hết hạn.
- Tăng tính toàn vẹn dữ liệu bằng transaction, row lock và partial unique index.
- Cải thiện khả năng bảo trì nhờ ranh giới trách nhiệm rõ hơn giữa Orders, Payments, Promotions và Inventory.
- Tăng độ tin cậy trước bàn giao thông qua quality gates tự động.

      → đọc lại state/deadline
      → nếu vẫn hợp lệ: chuyển CANCELLED
      → ghi OrderStatusHistory
      → release coupon
      → release inventory reservation
      → commit

### 4.4. Coupon validation và truyền coupon đến Order

    User nhập coupon trong CartDrawer
      → validateCoupon()
      → authenticatedRequest + JWT
      → POST /api/v1/coupons/validate
      → PromotionsService kiểm tra điều kiện
      → hợp lệ: trả quote preview, UI lưu couponCode/subtotal/discount
      → CartDrawer → menu/page.tsx → checkout/session.ts
      → Checkout kiểm tra quote còn khớp subtotal
      → POST /orders { items, couponCode }
      → backend tính lại giá và điều kiện coupon
      → Order response là nguồn chính thức cho subtotal/discount/total

Quote tại browser chỉ là preview và dữ liệu điều hướng; backend phải tính lại điều kiện/giá khi tạo Order. Validate coupon không thay thế việc reserve, consume hoặc release redemption ở backend.

### 4.5. Payment UI và idempotent retry

    Checkout nhận Order response
      → tạo Idempotency-Key cho lần thử Payment
      → lưu orderId + method + key + cart fingerprint vào sessionStorage
      → POST /payments với cùng Idempotency-Key
      → SUCCEEDED: clear Cart + pending checkout + coupon, chuyển confirmation
      → FAILED xác định: giữ orderId, bỏ key cũ, lần retry tạo key mới
      → PROCESSING / timeout / mất response: giữ nguyên orderId và key
      → reload: phục hồi pending attempt và replay POST cùng key

- Synchronous ref khóa double-click trước khi React re-render.
- Payment chưa rõ kết quả không được tự đổi method hoặc tạo Order mới.
- Nút “Kiểm tra trạng thái giao dịch” gọi GET /payments/status bằng Idempotency-Key đã lưu. Chỉ khi trả PAYMENT_NOT_FOUND mới replay POST /payments bằng chính key cũ; PROCESSING/UNKNOWN tiếp tục giữ nguyên Order và key.
- Lần retry sau FAILED dùng lại cùng Order nhưng key mới; đây là hành vi khác với replay khi outcome chưa xác định.

### 7.1. Quyết định kiến trúc (Architectural Decisions)

#### A. Payment status lookup — read-only, ownership-scoped

- Bổ sung `GET /api/v1/payments/status`, nhận `Idempotency-Key` qua header và danh tính Customer từ JWT.
- Repository chỉ trả trạng thái Payment nếu Payment có key đó gắn với Order thuộc đúng Customer hiện tại; key không tồn tại hoặc thuộc người khác trả `404 PAYMENT_NOT_FOUND`.
- Service chỉ đọc các trường `orderId`, `status`, `gatewayTransactionId`, `failureCode`; endpoint không gọi gateway, không tạo Payment mới và không sửa Order/Payment.
- Frontend khi phục hồi pending attempt sẽ gọi GET trước; `PROCESSING` tiếp tục giữ nguyên key, Order và phương thức.
- Chỉ khi GET trả `PAYMENT_NOT_FOUND` mới replay POST bằng **chính Idempotency-Key đã persist trước đó**; không cấp key mới trong trường hợp kết quả chưa xác định.
- Chỉ kết quả `FAILED` đã được persist mới cho phép retry nghiệp vụ bằng key mới trên cùng Order còn hạn.

**Giới hạn quan trọng:** endpoint này cải thiện khả năng quan sát và phân biệt “chưa có Payment row” với “Payment vẫn PROCESSING”; nó **không phải recovery operation**. Nếu Payment row đã commit và tiến trình chết sau khi gateway thực hiện charge nhưng trước khi cập nhật kết quả, hệ thống vẫn giữ `PROCESSING` để tránh double-charge. Cần gateway status inquiry/reconciliation và recovery command/API có authorization, audit, idempotency ở work item riêng trước khi tự động hóa.

#### B. Expiry lifecycle — một job có thẩm quyền ở cấp Order

- Chọn `OrderExpiryJob` làm expiry owner duy nhất; job đã được đăng ký trong `OrdersModule`, scheduler được bật tại `AppModule`.
- Job khóa Order, đọc lại trạng thái/deadline, kiểm tra Payment `PROCESSING` lần nữa, sau đó cập nhật Order/history và release coupon/reservations trong cùng transaction.
- Xóa `InventoryExpiryJob` và unit spec riêng vì class chưa được đăng ký; cách scan reservation rồi gọi release ở transaction riêng không có Order row lock và có thể race với Payment bắt đầu sau lần scan.
- Integration suite hiện có trong `inventory-expiry.integration-spec.ts` thực chất khởi chạy `OrderExpiryJob`; test giữ nguyên kiểm tra release reservation đúng một lần và không giải phóng tài nguyên khi Payment còn PROCESSING.

**Trade-off:** không có một cron độc lập chuyên quét reservation không gắn với một Order lifecycle; đổi lại mọi reservation của Order được giải phóng theo quyết định atomic của Order, tránh hai cron cạnh tranh và tránh release ngoài aggregate lock.

#### C. Migration — forward-only correction

- Giữ nguyên hai migration cũ để bảo toàn checksum/lịch sử môi trường đã deploy.
- Thêm `20261103030000_dedupe_payment_processing_index` để fail-fast nếu canonical index `uq_one_processing_payment_per_order` bị thiếu. Migration này còn dùng sai tên index khi DROP; corrective forward migration `20261103040000_drop_misspelled_duplicate_payment_index` đã drop đúng `payments_one_processing_per_order_key`, giữ lại canonical index.
- Tăng cường `migration-smoke.mjs`: sau `migrate deploy` hai lần và `migrate status`, truy vấn `pg_indexes` để xác nhận chỉ còn đúng một partial unique index cho Payment `PROCESSING`.

**Trade-off:** migration sẽ fail-fast nếu index chuẩn bị thiếu; không cố tự tạo lại index trong một migration dọn dẹp, vì việc đó có thể che giấu trạng thái database/migration history bất thường.

## 7.9. VNPay implementation update — 03/11/2026

### Quyết định kiến trúc

- Thêm PaymentMethod VNPAY cùng gateway_reference unique và payment_url được lưu trên Payment row.
- VnpayGatewayService tạo VNPay 2.1.0 payment URL, HMAC-SHA512, amount VND × 100, timestamp GMT+7 và reference ngẫu nhiên.
- Checkout persist Order ID + Idempotency-Key trước khi redirect; replay cùng key trả lại đúng URL đã persist.
- Signed IPN là nguồn quyết toán duy nhất; service lock Order, đọc lại Payment, kiểm tra merchant/amount rồi cập nhật Payment + Order trong cùng transaction.
- Return URL chỉ redirect về Checkout; không settlement từ browser query.
- VNPay disabled-by-default và fail-closed nếu thiếu credentials/HTTPS URLs.

### Acceptance boundary

- Gateway signature/URL, same-key replay, callback idempotency, amount/signature rejection và Return non-settlement được kiểm thử tự động.
- Chưa xác minh merchant TmnCode/HashSecret thật, domain HTTPS/IPN registration, Cloudflare Published Application hoặc giao dịch Sandbox end-to-end.
- Payment PROCESSING nếu thiếu IPN vẫn cần inquiry/reconciliation và recovery có authorization/audit; không được đánh dấu FAILED chỉ do timeout.
