## 1. Quyết Định Kiến Trúc & Hướng Đi Kỹ Thuật (Architectural Decisions)

### 1.1 Hướng đi được lựa chọn

Tiếp tục giữ phân lớp hiện tại:

- **PaymentsController:** nhận POST /api/v1/payments, bắt buộc header Idempotency-Key, lấy Order và số tiền từ backend.
- **PaymentsService:** tính SHA-256 requestHash, điều phối trạng thái Order/Payment, transaction và gateway.
- **PaymentsRepository:** truy vấn/ghi Payment qua Prisma; cho phép truy vấn bằng Prisma transaction client.
- **PostgreSQL:** unique constraint trên payments.idempotency_key và partial unique index chỉ cho phép một Payment PROCESSING trên mỗi Order.

Điểm sửa trọng tâm là **double-check Idempotency-Key bên trong transaction sau khi đã khóa Order**. Lần lookup đầu xử lý replay thông thường. Lần lookup thứ hai dùng transaction client giúp request đến sau quan sát Payment do request thắng cuộc tạo ra sau khi row lock được giải phóng.

Với xung đột unique key toàn hệ thống giữa hai Order khác nhau (không thể được tuần tự hóa chỉ bằng row lock của một Order), service xử lý Prisma P2002 bằng cách truy vấn lại key:

- Hash khác → trả 409 IDEMPOTENCY_KEY_REUSED.
- Hash giống và Payment còn PROCESSING → trả 409 PAYMENT_IN_PROGRESS.
- Payment đã ở trạng thái kết thúc → trả kết quả đã lưu, không gọi gateway lần nữa.
- Không tìm thấy key → coi đây là xung đột invariant Payment PROCESSING trên cùng Order, trả 409 PAYMENT_IN_PROGRESS.

### 1.2 Lý do lựa chọn (Rationales)

1. **Không dựa vào check-then-insert đơn thuần.** Hai request có thể cùng đọc “chưa tồn tại” rồi cùng ghi. Lần kiểm tra lại sau row lock đóng race trong cùng Order.
2. **Không dùng application mutex.** Mutex trong một Node process không bảo vệ nhiều replica, worker hoặc process khác. PostgreSQL là nguồn đồng bộ cuối cùng.
3. **Không nuốt mọi lỗi P2002 thành cùng nguyên nhân.** Truy vấn lại key phân biệt key bị tái sử dụng với xung đột “một Payment PROCESSING trên một Order”.
4. **Không gọi gateway khi đang giữ Order row lock.** I/O bên ngoài không nên kéo dài transaction và giữ khóa DB. Gateway hiện tại vẫn chạy sau transaction tạo Payment.
5. **Không tin amount do browser gửi.** Controller lấy Order.total từ DB; requestHash được tính tại backend từ orderId, method và amount thực tế.

### 1.3 Trade-off Analysis

| Phương án | Đánh giá |
|---|---|
| Chỉ query key rồi insert | Loại bỏ: race condition check-then-insert |
| In-memory mutex | Loại bỏ: không bảo vệ nhiều instance/process |
| Chỉ unique index rồi luôn trả PAYMENT_IN_PROGRESS | Chưa đủ: key khác payload có thể bị báo sai mã lỗi |
| Khóa Order + re-check key trong transaction + unique-index fallback | Chọn: bảo vệ same-order race và global key collision |
| Chờ request thứ hai tới khi gateway hoàn tất | Không chọn: có thể giữ HTTP request lâu; API dùng 409 để client kiểm tra/replay |
| Cắm VNPay vào synchronous charge flow hiện tại | Chưa chọn: VNPay cần redirect trình duyệt và server-to-server IPN bất đồng bộ; phải thiết kế lifecycle riêng |

### 1.4 Giá trị mang lại (Value Proposition)

- Cùng key/cùng request không tạo Payment thứ hai và không gọi gateway hai lần.
- Cùng key/khác request bị phát hiện chính xác cả khi request đến đồng thời.
- Hai key khác nhau nhưng cùng Order vẫn được partial unique index bảo vệ.
- Kết quả cuối được replay từ DB thay vì phát sinh side effect lần nữa.
- Có kiểm thử cạnh tranh PostgreSQL thật; không chỉ dựa trên mock service.

### 1.5 Hướng tích hợp VNPay — quyết định và giới hạn hiện tại

VNPay Sandbox phải được xem là **redirect payment provider**, không phải một hàm giả lập backend trả về SUCCESS:

1. Backend tạo Payment và URL đã ký HMAC-SHA512.
2. Browser chuyển hướng tới VNPay.
3. VNPay gọi IPN server-to-server để merchant xác minh chữ ký, TxnRef, amount và trạng thái, rồi cập nhật DB.
4. Return URL chỉ xác minh/trình bày kết quả. Không dùng Return URL làm nguồn quyết định Payment đã PAID.

Tài liệu chính thức: [VNPay — Kết nối Cổng thanh toán](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html). Tài liệu quy định URL Sandbox, TmnCode/HashSecret, chữ ký, amount nhân 100, IPN cần SSL và kiểm tra checksum trước khi xử lý.

**Chưa triển khai trong commit này:** adapter VNPay, schema lưu payment URL/provider reference, endpoint Return/IPN, xác thực chữ ký, xử lý IPN lặp, UI redirect/đọc trạng thái sau callback. Đây là phần tiếp theo vì cần thiết kế luồng bất đồng bộ và có Merchant credentials + HTTPS endpoint để nghiệm thu đầu-cuối. Không thay MockGateway bằng mã “giả VNPay” hoặc hardcode secret.

Các quyết định bắt buộc cho increment VNPay:

- Tách gateway contract thành kết quả đồng bộ (Mock) và redirect (VNPay), không ép redirect vào charge(): Promise<{success:boolean}>.
- Lưu merchant TxnRef và URL thanh toán (hoặc đủ dữ liệu để tái tạo cùng URL) để replay cùng key vẫn dùng đúng giao dịch.
- IPN là nguồn cập nhật trạng thái có tính quyết định; xác minh HMAC trước lookup/side effect, đối chiếu TmnCode, TxnRef, amount, ResponseCode và TransactionStatus.
- Dùng transaction/row lock khi chuyển Payment và Order; callback lặp không lặp side effect.
- Return URL chỉ redirect người dùng về UI; UI đọc trạng thái Order/Payment từ API BrewLite.
- Giữ MockGateway cho CI/local test.

### 2.1 apps/api/src/modules/payments/services/payments.service.ts

**Mục đích:** xử lý replay thống nhất và đóng race giữa hai request cùng key.

- **Dòng 21–52 — resolveExistingPayment():** gom logic Payment đã tồn tại. So sánh requestHash trước; khác hash trả IDEMPOTENCY_KEY_REUSED; cùng hash + PROCESSING trả PAYMENT_IN_PROGRESS; trạng thái kết thúc trả kết quả đã lưu với isRetried=true.
- **Dòng 70–74 — preflight lookup:** giữ lookup key ban đầu để replay thông thường không cần tạo transaction.
- **Dòng 80–98 — transaction + row lock + transactional re-check:** sau getOrderForPaymentForUpdate(), gọi findByIdempotencyKey(idempotencyKey, tx). Nếu transaction trước đã commit Payment cùng key, request hiện tại xử lý như replay; không tạo Payment mới.
- **Dòng 100–136 — kiểm tra Order và tạo Payment:** giữ guard PAID, trạng thái cho phép và reservation expiry; retry PAYMENT_FAILED và create PROCESSING vẫn nằm cùng transaction.
- **Dòng 138–166 — P2002 fallback:** nếu transaction phát hiện key đã có, gọi resolver. Nếu unique constraint phát nổ trong race giữa Order khác nhau, re-query key toàn cục để phân biệt hash mismatch, in-progress và order-level conflict.
- **Dòng 185 trở đi — gateway:** vẫn gọi MockGateway sau transaction tạo Payment. Đây là bằng chứng VNPay chưa được wiring trong increment này.

**Coding intent:** kiểm tra lần hai phải nằm sau row lock và dùng đúng transaction client. Nếu đặt ngoài transaction, khoảng race giữa SELECT và INSERT vẫn còn.

### 3.7 VNPay Sandbox — chuẩn bị cho increment kế tiếp

Đăng ký/nhận thông tin merchant tại [VNPay Sandbox dev registration](http://sandbox.vnpayment.vn/devreg/). Cấu hình secret ở môi trường backend, không ghi vào Git:

- VNP_TMN_CODE
- VNP_HASH_SECRET
- VNP_PAYMENT_URL (sandbox mặc định: https://sandbox.vnpayment.vn/paymentv2/vpcpay.html)
- VNP_RETURN_URL (HTTPS public URL tới backend Return handler)
- VNP_IPN_URL (HTTPS public URL tới backend IPN handler)
- WEB_PUBLIC_URL (frontend URL để backend Return handler redirect người dùng về UI)

Đây là danh sách cấu hình đề xuất cho phần tích hợp tiếp theo; các biến này chưa được đọc bởi implementation hiện tại.

Theo tài liệu VNPay:
- vnp_Amount gửi bằng amount VND nhân 100.
- HMACSHA512 checksum được tạo trên tham số đã sort theo tên.
- IPN cần HTTPS; xác thực checksum trước khi xử lý và đối chiếu TxnRef/amount/status.
- Return URL không nên tự cập nhật Payment/Order là PAID; chờ IPN và đọc trạng thái từ DB.

Nguồn: [VNPay Payment API docs](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html).

### 3.8 Public HTTPS tunnel cho nhóm — trade-off

**Đề xuất ưu tiên:** Cloudflare Named Tunnel + hostname thuộc domain nhóm quản lý, nếu nhóm có domain và quyền quản trị DNS/Cloudflare. DNS CNAME trỏ hostname tới tunnel UUID (<UUID>.cfargotunnel.com); hostname ổn định khi tunnel host còn chạy. Tài liệu: [Cloudflare Published Applications](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/) và [DNS records](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/dns/).

**Phương án tạm thời:** ngrok Free cấp một dev domain riêng cho account, domain không đổi khi agent khởi động lại. Tuy nhiên gói Free giới hạn 1 team member, 1 GB bandwidth/tháng, 20.000 HTTP/S requests/tháng, tối đa 3 endpoint và browser interstitial; custom domain không nằm trong Free. Phù hợp cho một owner chạy sandbox endpoint, không phải tài khoản team nhiều thành viên. Xem [ngrok pricing](https://ngrok.com/pricing) và [Static dev domains](https://ngrok.com/blog/free-static-domains-ngrok-users).

**Không dùng Cloudflare Quick Tunnel làm endpoint dùng chung lâu dài:** hostname tạm thời thay đổi khi tạo lại tunnel. Quick tunnel có ích cho một lần demo, không thay thế Named Tunnel + DNS ổn định.

**Điều kiện vận hành:** cần một máy/VM hoặc dev host được chỉ định chạy backend và tunnel liên tục khi VNPay gọi IPN. URL tunnel chỉ cung cấp ingress; nó không tự triển khai backend, không cấp merchant credentials và không biến callback thành production environment.

### 4.2 Luồng hiện tại — POST /payments

~~~mermaid
sequenceDiagram
  participant UI as Checkout UI
  participant API as PaymentsController
  participant S as PaymentsService
  participant O as OrdersService
  participant R as PaymentsRepository
  participant DB as PostgreSQL
  participant G as MockGatewayService

  UI->>UI: Tạo/persist Idempotency-Key trước POST
  UI->>API: POST /api/v1/payments + Idempotency-Key
  API->>O: Lấy Order thuộc user và amount từ DB
  API->>S: processPayment(key, orderId, userId, method, amount)
  S->>R: findByIdempotencyKey(key)
  alt key đã tồn tại
    S->>S: resolveExistingPayment(requestHash)
    S-->>UI: Replay cũ hoặc 409
  else key chưa tồn tại
    S->>DB: BEGIN
    S->>O: SELECT Order FOR UPDATE
    S->>R: findByIdempotencyKey(key, tx)
    alt key vừa được request khác tạo
      S->>DB: END
      S-->>UI: Replay cũ hoặc 409; không gọi Gateway
    else vẫn chưa có key
      S->>DB: Check Order state + expiry; create Payment PROCESSING
      S->>DB: COMMIT
      S->>G: charge(amount, method) ngoài transaction
      G-->>S: success/failure
      S->>DB: BEGIN; cập nhật Payment + Order; COMMIT
      S-->>UI: Kết quả thanh toán
    end
  end
~~~

### 4.3 Các nhánh cạnh tranh được kiểm chứng

1. **Cùng Order + cùng key + cùng payload:** row lock tuần tự hóa hai request; request sau đọc được key trong transaction và không gọi Gateway lần hai.
2. **Cùng Order + cùng key + khác payload:** transaction sau tìm thấy Payment nhưng requestHash khác → IDEMPOTENCY_KEY_REUSED.
3. **Khác Order + cùng key + khác payload:** hai Order khóa độc lập; global unique key constraint chọn insert thắng, request thua re-query key rồi phân biệt hash mismatch.
4. **Khác key + cùng Order:** partial unique index uq_one_processing_payment_per_order chỉ cho phép một Payment PROCESSING tại một thời điểm.

### 4.4 Luồng VNPay mục tiêu — chưa triển khai

~~~mermaid
flowchart TD
  A[Checkout] --> B[POST payment + Idempotency-Key]
  B --> C[Create/replay PROCESSING Payment]
  C --> D[Build signed VNPay URL]
  D --> E[Browser redirects to VNPay Sandbox]
  E --> F[VNPay server calls HTTPS IPN]
  F --> G[Verify HMAC, TmnCode, TxnRef, amount, status]
  G --> H[DB transaction: Payment + Order exactly once]
  E --> I[Browser Return URL]
  I --> J[Verify signature then redirect to BrewLite UI]
  J --> K[UI reads authoritative Payment/Order state from BrewLite API]
  H --> K
~~~

Return URL không phải nguồn quyết toán. IPN phải là server-to-server update đã xác minh, idempotent và được bảo vệ bởi transaction/unique constraints.
