### **ĐẶC TẢ USE CASE: UC-01 - ĐĂNG KÝ TÀI KHOẢN**

| Tên mục | Nội dung chi tiết |
| :--- | :--- |
| **Tên Use Case** | Đăng ký tài khoản khách hàng (Customer Account Registration) |
| **Mã Use Case** | UC-01 |
| **Sequence Diagram liên kết** | SD-05: Sequence Diagram Đăng ký tài khoản (Sprint 1 / Task Auth) |
| **Tác nhân (Actors)** | Khách hàng vãng lai (Guest / Customer) |
| **Tóm tắt (Brief Description)** | Use case mô tả quy trình một khách hàng mới tạo tài khoản thành viên trong hệ thống BrewLite để sử dụng các dịch vụ đặt đồ uống, lưu lịch sử đơn hàng và tham gia chương trình tích lũy điểm thưởng (Loyalty Program). Trọng tâm bảo mật của use case này là mật khẩu bắt buộc phải được băm một chiều an toàn bằng bcrypt trước khi lưu xuống cơ sở dữ liệu, ngăn chặn trùng lặp email/tài khoản và cấp phát JWT Access Token để người dùng tự động đăng nhập ngay sau khi đăng ký thành công. |
| **Tiền điều kiện (Pre-conditions)** | - Khách hàng chưa đăng nhập vào hệ thống.<br>- Phân hệ xác thực (Auth Module) và cơ sở dữ liệu PostgreSQL đang hoạt động bình thường. |
| **Hậu điều kiện (Post-conditions)** | - Bản ghi người dùng mới được lưu thành công trong bảng `users` với vai trò mặc định `CUSTOMER`, số dư điểm thưởng `loyalty_balance = 0`, trạng thái `is_active = true`.<br>- Mật khẩu được băm an toàn dưới cột `password_hash`, tuyệt đối không lưu plaintext.<br>- Người dùng nhận được JWT Access Token hợp lệ (thời hạn 15 phút) và được tự động đăng nhập.<br>- Tuyệt đối không để lộ chuỗi băm mật khẩu trong response DTO, exception hay log server. |
| **Dòng sự kiện chính (Happy Path)** | **1.** Khách hàng truy cập vào trang Đăng ký trên Web (`/register`), nhập đầy đủ thông tin: Email/Username, Mật khẩu và Xác nhận mật khẩu, sau đó bấm nút "Đăng ký".<br><br>**2.** Giao diện Frontend kiểm tra sơ bộ tính hợp lệ (Client-side validation): Định dạng email hợp lệ, độ dài mật khẩu tối thiểu 8 ký tự, hai ô mật khẩu trùng khớp nhau.<br><br>**3.** Frontend gửi yêu cầu HTTP `POST /api/v1/auth/register` kèm payload `RegisterDto` lên Backend API.<br><br>**4.** Backend (`ValidationPipe`) thẩm định dữ liệu đầu vào theo quy chuẩn strict whitelist.<br><br>**5.** Backend (`AuthService`) truy vấn cơ sở dữ liệu để kiểm tra tính duy nhất của Username/Email: Hệ thống xác nhận tài khoản chưa từng tồn tại.<br><br>**6.** Backend tiến hành băm mật khẩu bằng thư viện **bcrypt** với hệ số an toàn `saltRounds = 10`.<br><br>**7.** Backend gọi `UserRepository` lưu bản ghi người dùng mới vào cơ sở dữ liệu PostgreSQL thông qua Prisma ORM.<br><br>**8.** Backend tạo chữ ký và phát hành **JWT Access Token** (chứa thông tin: `sub`, `username`, `role = CUSTOMER`) có hiệu lực trong 15 phút.<br><br>**9.** Backend phản hồi HTTP `201 Created` kèm theo đối tượng thông tin người dùng và Access Token (đã loại bỏ hoàn toàn trường `passwordHash`).<br><br>**10.** Frontend lưu token vào bộ nhớ/phiên làm việc, cập nhật trạng thái đăng nhập và tự động điều hướng khách hàng sang trang Thực đơn (`/menu`). |
| **Dòng sự kiện thay thế (Alternative Paths)** | **Khách hàng đã có tài khoản:**<br>Tại bước 1, nếu khách hàng nhận ra mình đã có tài khoản, khách hàng bấm vào liên kết "Đã có tài khoản? Đăng nhập ngay". Hệ thống lập tức chuyển hướng người dùng sang trang Đăng nhập (**UC-02**). |
| **Dòng sự kiện ngoại lệ (Exceptions)** | **1. Ngoại lệ dữ liệu đầu vào không hợp lệ (Validation Error):**<br>Tại bước 2 hoặc bước 4, người dùng nhập email sai quy cách hoặc mật khẩu ít hơn 8 ký tự. Hệ thống từ chối xử lý, trả về mã lỗi HTTP `400 Bad Request` kèm mã lỗi `VALIDATION_ERROR` và chi tiết các trường bị vi phạm. Frontend hiển thị thông báo lỗi rõ ràng bên dưới từng ô nhập liệu tương ứng.<br><br>**2. Ngoại lệ tài khoản/email đã tồn tại (Conflict Error):**<br>Tại bước 5, hệ thống phát hiện Username/Email đã được người khác đăng ký trước đó. Backend dừng xử lý và trả về HTTP `409 Conflict` kèm mã lỗi chuẩn `USERNAME_ALREADY_EXISTS`. Frontend hiển thị thông báo: *"Email hoặc tài khoản này đã được đăng ký. Vui lòng sử dụng email khác hoặc đăng nhập."*<br><br>**3. Ngoại lệ gián đoạn hạ tầng (Server/Database Error):**<br>Nếu cơ sở dữ liệu tạm thời mất kết nối, Backend ghi log có cấu trúc và trả về HTTP `500 Internal Server Error`. Giao diện hiển thị thông báo thân thiện: *"Hệ thống đang bảo trì, vui lòng thử lại sau ít phút."* |
| **Quy tắc nghiệp vụ & Bảo mật (Business Rules)** | - **Chuẩn thuật toán băm:** Sử dụng BCrypt với cost factor (salt rounds) tối thiểu là 10.<br>- **Tính toàn vẹn dữ liệu:** Cột `username` trong bảng `users` được ràng buộc duy nhất (UNIQUE CONSTRAINT).<br>- **Khởi tạo dữ liệu:** Điểm thưởng khách hàng khởi tạo bằng 0 (`loyalty_balance = 0`), tài khoản kích hoạt sẵn (`is_active = true`).<br>- **Chuẩn hóa phản hồi lỗi:** Tất cả response lỗi đều tuân thủ cấu trúc envelope chuẩn của BrewLite: `{ error: { code, message, details, requestId } }`. |
