### **ĐẶC TẢ USE CASE: UC-08 \- THỰC HIỆN THANH TOÁN (Mock Gateway & Idempotency)**

| Tên mục | Nội dung chi tiết |
| :---- | :---- |
| **Tên Use Case** | Thực hiện thanh toán (Mock Gateway & Idempotency) |
| **Tên Actor** | Khách hàng, Mock Payment Gateway |
| **Tóm tắt** | Use case mô tả quá trình khách hàng thực hiện thanh toán cho một đơn hàng (đã được tạo) thông qua cổng thanh toán giả lập. Trọng tâm của UC này là xử lý cơ chế chống trùng lặp (Idempotency) dựa vào Idempotency-Key và Request-Hash để đảm bảo dù khách hàng gửi lại request nhiều lần, họ cũng chỉ bị trừ tiền đúng một lần. |
| **Dòng sự kiện chính *(Happy Path)*** | 1\. Khách hàng gửi yêu cầu thanh toán kèm Header Idempotency-Key và payload (thông tin đơn, số tiền).<br><br>2\. Hệ thống kiểm tra Idempotency-Key: Khóa này **chưa từng tồn tại** trong hệ thống.<br><br>3\. Hệ thống ghi nhận khóa này với trạng thái *"Đang xử lý"*.<br><br>4\. Hệ thống gọi sang **Mock Payment Gateway** để tiến hành thanh toán.<br><br>5\. Mock Gateway giả lập xử lý và trả lời *"Thành công"*.<br><br>6\. Hệ thống cập nhật bản ghi của Idempotency-Key thành *"Thành công"* và lưu kết quả trả về.<br><br>7\. Hệ thống trả về HTTP 200/201 kèm trạng thái PAID cho Khách hàng. |
| **Dòng sự kiện thay thế *(Retry Path)*** | *(Xảy ra khi user mạng lag bấm F5 hoặc app tự động retry)* 1\. Tại bước 2 của luồng chính, hệ thống phát hiện Idempotency-Key **đã tồn tại**, đồng thời Request-Hash (nội dung payload) khớp với lần gửi trước.<br><br>2\. Hệ thống kiểm tra thấy trạng thái của khóa này đã là *"Đã hoàn thành"* (Thành công/Thất bại).<br><br>3\. Hệ thống **BỎ QUA** việc gọi sang Mock Payment Gateway (để không trừ tiền lặp lại).<br><br>4\. Hệ thống lấy ngay kết quả đã lưu từ lần trước và trả về cho Khách hàng. |
| **Dòng sự kiện ngoại lệ *(Exceptions)*** | 1\. **Ngoại lệ Gateway từ chối (Random Fail):** Tại bước 5 luồng chính, Mock Gateway giả vờ hết tiền/lỗi thẻ và trả về "Thất bại". Hệ thống cập nhật khóa thành "Thất bại" và trả về HTTP 400 kèm status PAYMENT\_FAILED.<br><br>2\. **Ngoại lệ thay đổi Payload (Hash Mismatch):** Khách dùng lại Idempotency-Key cũ nhưng cố tình đổi số tiền (làm Hash bị khác). Hệ thống từ chối ngay lập tức, trả lỗi HTTP 400 Bad Request.<br><br>3\. **Ngoại lệ Đua lệnh (Race Condition):** Khách spam click 2 lần liên tục. Request 2 lao tới khi Request 1 vẫn đang ở bước 3 (Đang xử lý). Hệ thống trả về HTTP 409 Conflict yêu cầu khách đợi. |
| **Tiền điều kiện *(Pre-condition)*** | \- Module Payments đã sẵn sàng hoạt động. \- Khách hàng (Client) gửi yêu cầu thanh toán (chứa order\_id, amount, currency...) bắt buộc phải kèm theo Header: Idempotency-Key (một chuỗi UUID duy nhất) và Request-Hash (mã băm của nội dung request). |
| **Hậu điều kiện *(Post-condition)*** | \- Kết quả thanh toán cuối cùng của request phải là PAID (Thành công) hoặc PAYMENT\_FAILED (Thất bại). \- Trạng thái kết quả của Idempotency-Key được lưu lại (cache/DB) để phục vụ cho các lần gửi lại sau này. *(**Lưu ý Sprint 1:** Ta chỉ giả lập trả về kết quả ra API cho đúng hợp đồng, chưa gọi Service để trực tiếp can thiệp đổi trạng thái Order trong DB của Khang).* |
