## 2. Kết quả review độc lập — Senior Staff Engineer

### P0/P1 — Một Order có thể có nhiều VNPay payment attempt đang PROCESSING

**Phát hiện:** VNPay giữ Order ở trạng thái `PENDING` trong lúc khách hàng được redirect ra cổng thanh toán. Code cũ chỉ khóa dòng Order và kiểm tra Idempotency-Key; hai request cùng Order nhưng dùng hai key khác nhau vẫn có thể tạo hai Payment `PROCESSING`, mỗi Payment có một `gatewayReference` và payment URL riêng. Cả hai URL đều có thể được thanh toán. IPN thứ hai bị từ chối sau khi Order đã PAID nhưng không thể đảo ngược khoản thu thứ hai ở phía ngân hàng.

**Sửa trong branch:**
- Thêm repository query tìm Payment `PROCESSING` theo Order bên trong transaction đã khóa Order.
- Từ chối tạo attempt mới với `PAYMENT_IN_PROGRESS` khi Order đã có attempt chưa có kết quả cuối cùng.
- Thêm partial unique index PostgreSQL trên `payments(order_id)` với predicate `status = 'PROCESSING'`, bảo vệ invariant ở tầng database ngay cả khi có đường ghi khác hoặc race.
- Thêm unit regression test cho request dùng Idempotency-Key khác nhưng cùng Order đang có Payment PROCESSING; thêm repository test cho truy vấn.

### Các điểm tốt

- Request hash được tính từ Order, method và amount; amount lấy từ Order trong DB chứ không nhận từ client.
- Unique constraint trên Idempotency-Key và gateway reference là lớp bảo vệ hữu ích.
- Order row lock được dùng trong transaction để serialize thanh toán với expiry/retry.
- Mock gateway I/O nằm ngoài transaction giữ lock.
- VNPay dùng HMAC-SHA512, so sánh chữ ký constant-time, kiểm tra merchant code và amount theo đơn vị VNPay.
- Return URL không tự quyết toán; IPN là đường cập nhật trạng thái.
- Callback IPN cập nhật Payment và Order trong cùng transaction.
- Gateway mock vẫn là mặc định khi không bật VNPay.

### Các điểm yếu / rủi ro còn lại

1. **P1 — Late IPN sau khi Order hết hạn/hủy:** nếu expiry worker thắng lock và chuyển Order sang trạng thái không còn nhận thanh toán, IPN thành công đến muộn sẽ bị trả `02`. Nếu ngân hàng đã thu tiền, hệ thống hiện không có luồng ghi nhận khoản thu muộn và refund/reconciliation tự động. Cần sandbox test và thiết kế compensation/reconciliation trước production.
2. **P1 — Payment PROCESSING không có lease/reaper rõ ràng:** nếu người dùng bỏ redirect hoặc IPN không đến, attempt có thể giữ Order ở trạng thái đang thanh toán cho tới khi expiry. Cần quy trình truy vấn trạng thái gateway hoặc vận hành đối soát; không được tự ý tạo attempt thứ hai vì nguy cơ double-charge.
3. **P1 — Chưa có VNPay Merchant Sandbox end-to-end:** cấu hình ký và mock test không chứng minh callback thực tế, merchant account, tunnel, IPN retries hay response code mapping.
4. **P2 — `normalizeQuery` chọn phần tử đầu khi query param lặp:** nên reject duplicate parameter thay vì âm thầm chọn giá trị đầu, tránh khác biệt parser/canonicalization.
5. **P2 — IP address phụ thuộc proxy trust configuration:** cần xác nhận Express/Nest trust proxy chỉ tin proxy được kiểm soát; không coi `request.ip` là tin cậy nếu client có thể giả mạo forwarded headers.
6. **P2 — Không có bằng chứng lịch sử RED-before-GREEN cho toàn bộ implementation:** test hiện tại là regression coverage, không phải bằng chứng TDD theo từng commit cho toàn bộ VNPay.
7. **P2 — Coverage tổng thể không thay thế coverage theo nhánh rủi ro:** cần kiểm tra duplicate callback, callback đến đồng thời, amount boundary, malformed/repeated query params, expiry race và transaction rollback.
